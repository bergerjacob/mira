## 2. What already exists (so we don't reinvent it)

**Avatar/harness layer - saturated, do not build another.**
- Mineflayer (PrismarineJS) and everything on it: **Mindcraft** (LLM + skill library + generated code, has construction tasks), many MCP servers (`yuniko-software/minecraft-mcp-server`, 61-tool variants), `yc-software/minecraft-agent-harness` (runs agents via pi).
- Known weakness, same as you suspected: placing as a character is gated by pathfinding, reach, line-of-sight and inventory, one block per action. One MCP project's own plan doc calls it "the wrong abstraction for a build engine" (could not re-fetch; **unverified**).

**Build-as-code - the norm, and it is what we already do.**
- Minedit (NeoForge mod; model writes builder JS in a sandbox, capped ops, supports staged generation and line-aware patch edits), MineBench (raw coords JSON, plus a `voxel.exec` tool mode with `block/box/line` primitives for builds beyond token limits), Schematica/Litematica-GPT style tools, Nucleation's primitives/SDF.
- Benchmarks: MineCEraft (EMNLP Findings 2026; 723 tasks, programmatic checks incl. floating-block BFS and von Mises stress; frontier models ~27-40% problem-level vs humans far higher, in a Mindcraft-style agent), MineAnyBuild, MC-Bench (human voting), Redstone Bench (**site is placeholder mock data, no real results**).

**Redstone-specific - this is the interesting part.**
- **Nucleation** (Schem-at, Rust, `pip install nucleation`, Python 3.12+, MIT, actively updated Oct 2026): schematic engine + headless redstone simulation via MCHPRS Redpiler + a separate "vanilla-accurate" tick simulator (`mc-tick`) said to be verified against game captures + typed circuit executor (set inputs by integer, read outputs) + meshing/rendering. Its README also describes a Verilog->redstone EDA flow with DRC/LVS/STA and a 32-bit Kogge-Stone adder proven in the simulator (221,785 blocks across 18 artifacts). **Unverified**: I could not install it (sandbox blocks PyPI), so coverage of pistons/observers/dropper/hopper mechanics and parity with our Carpet results are unknown. MCHPRS docs list repeaters, comparators, torches, buttons, lamps, levers, pressure plates; an observer PR exists but was open as of mid-2025.
- Lemma Redstone MCP (npm, v0.2.7, Jul 2026, clean-room tick engine, design/simulate/place) - same idea, small/new. `RyanRana/minecraft-circuts` (Verilog/netlist -> blocks). MC-ticker (runs vanilla jar logic).
- **Nekochu/Gemma-4-31B-RedstoneDoor**: the closest prior art to our training goal. ~2 months, ~10 attempts, ~$300. GRPO from the base model produced **0 working 2x2 doors** (500 steps); only an overfit SFT (effectively memorising the door) worked; 3x3 stayed 0/96. Frontier models also mostly fail the 2x2 door from scratch (reports Opus 4.7 managed one design after heavy thinking).

**RL infrastructure.**
- **Bedrock-RL** + **Netherite** (deterministic C/CUDA reimplementation of Minecraft **1.7.10**, verl-based GRPO/RLOO/SFT/OPD, YAML tasks/rewards, redstone listed among supported task types). Good for vision/embodied RL; its 1.7.10 target means no modern redstone/piston-door parity and no 1.21 builds.
- Andy-4 / Mindcraft-CE: small fine-tuned models for Mindcraft play (3 weeks on one 3090). Survival/agentic play, not building.

## 3. What this says about our options

1. Our custom RCON harness is not novel. The avatar layer is done by others; the build-as-code layer is done by others. The only parts that are ours are the **verification contracts + Carpet/Scarpet ground truth + the procedural verified-circuit generators**.
2. For *computational* redstone (adders, ALUs, memory), a frontier model's best leverage is **writing a netlist/HDL and calling a compiler/router**, not placing blocks. Others already ship that pipeline (Nucleation EDA, minecraft-circuts). A harness that exposes it is mostly integration, not research.
3. Blind coordinate-level generation by open models is the least promising path (Nekochu result, our own 17.5% and ~0-40% frontier numbers on trivial circuits). Training only makes sense **after** there is a harness whose trajectories can be verified and sampled at scale.
4. A fast headless simulator removes our biggest bottleneck. Our Carpet loop needs a live server and RCON round-trips (per-build cost not re-measured today); a Rust sim is plausibly orders of magnitude cheaper (unmeasured), which is what makes RL/rejection sampling on HPC realistic. Whether it is faithful enough is the first thing to test.

## 4. Recommended direction

**Make the product a "build repository" harness for existing frontier agents (Claude Code/pi/Codex), not a new agent and not a new avatar bot.** Your instinct about visual/incremental work is the right fix for large builds: treat a build like a codebase instead of loading it into context.

- *Source of truth is a program, not blocks*: parametric build scripts / modules / netlists in files; edits are diffs; builds rebuild deterministically.
- *Views on demand* instead of full dumps: bbox/slice queries, per-layer ASCII, palette summaries, isometric/orthographic PNG renders (for vision-capable models), diff vs last version.
- *Checks as tools*: structural (floating blocks, support, bounding box), functional (simulator: set inputs, run N ticks, read outputs, truth-table/timing sweeps, waveform traces), and a final "paste into real Minecraft + Carpet confirm" step.
- *Component library*: retrieval over our 242-2,296 schematics + verified procedural generators.
- Delivered as an MCP server/CLI, thin on top of Nucleation if the spike passes (else on our Carpet bridge).

**Why this is also the best path to training.** The same environment gives (a) frontier-model trajectories to filter by verifier (expert iteration/SFT seed - Nekochu shows a seed is mandatory), then (b) GRPO with the sim as reward on procedurally generated tasks, on HPC. The contribution that I did not find already existing: a **redstone environment with machine-checkable specs (truth tables/timing), difficulty-scaled task generators, a fast simulator backend, and a harness-ablation study** (what actually moves a frontier model: iteration, probes, renders, netlist tools). Treat "I did not find it" as a prompt to double-check before claiming novelty.

## 5. Plan with decision gates

0. **Spike (1-2 h, needs PyPI access):** install Nucleation in a scratch venv; rebuild our 14 `tests/fixtures/circuits/*.json` and 12 `evaluation/test_circuits`; compare pass/fail and tick traces against Carpet. Gate: >=95% agreement on non-entity circuits and a list of unsupported mechanics. If it fails, keep Carpet and cap RL ambitions; if it passes, Carpet becomes the confirmation oracle.
1. **Fix the measurement** before collecting more numbers: fixed (not model-authored) specs, fix gemini client path, rerun frontier models with 0/1/3 feedback rounds to get the real iteration lift. Gate: iteration lift is large (e.g. >2x) -> harness story is real.
2. **Build the MCP harness v0** (build-script + views + sim/structural checks) and run Claude/GLM/DeepSeek through it on a ladder of tasks (lamp -> gates -> clocks -> piston door -> adders). Record trajectories.
3. **Benchmark + dataset release** (task generator + verifier + baseline table). Cheap to publish, and it is the contribution regardless of training.
4. **Training (only if 1-2 look good):** SFT on verified trajectories (~30B open model, LoRA, HPC), then GRPO with sim reward. Go/no-go on whether the tuned model closes a meaningful fraction of the gap to the frontier model inside the same harness.
5. **Data scraping:** low priority for functional training; only continue it to grow the retrieval library and for style priors. Prioritise labelling/tagging the existing 2,296 files (type, size, IO, entity-dependence) over scraping more.
