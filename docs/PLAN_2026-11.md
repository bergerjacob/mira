# MIRA plan (2026-11-02)

Supersedes the build order in `STACK_PROPOSAL.md`. Reasoning for each decision is in `docs/audits/oracle_*_2026-11.md`; this page is the working summary.

## Principle
The model edits a **build program** and calls **tools**. Everything is scored by a fast simulator against **author-written hidden specs**. A real-game oracle referees. The Carpet/RCON server is no longer in the scoring path.

```
model ──(Python Part API)──> simulation/builder.py ──> flat (x,y,z,state,nbt) blocks
                                                         │
                       env/  (contract v2, runner, R0-R4 reward, tools)  ── Nucleation TickSimulation (Placement settle)
                                                         │
                       tools/oracle  (vanilla MC 26.2 GameTest tracer, ~200 captures/s) ── referee / cross-check
```

## Next steps, in order
1. **Iteration-lift experiment** (running): 0/3/8 feedback rounds, blocks vs builder arm, cheap models. Decides whether the harness is worth more investment and which authoring arm wins. The OpenRouter key has about $3 left; bigger grids need a top-up.
2. **T3 and the library**: n-bit adders, decoders, counters; measure S50 (the build size at which pass rate falls below 50%) with and without the library and with the Nucleation compiler allowed, as separate tool tiers.
3. **Module layer** (registry, per-module specs, fault localisation) once T3 shows flat building breaking down.
4. **Fresh Discord token**, then run `discord_scraper/RUNBOOK.md`, then `scripts/corpus_index.py`. Priority servers are in `config.candidates.json`; Storage Catalog is better taken from its GitHub archive.
5. **Training data**: verified trajectories from step 1-3 (rejection SFT), reverse-curriculum starts from verified builds with parts deleted, corpus decompiles for repair/edit tasks only (most of the corpus is entity-dependent farms).
6. **Version decision**: Nucleation labels 5023 (26.3), the oracle is pinned to 26.2, the old Carpet server is 1.21.0. Pin 26.2 everywhere new, regenerate `blockstates_1_21.json` from a 26.2 data report.

## Known risks
- Nucleation bugs (comparator side input from a lever, dropper-into-dropper false trigger, torch burnout clock) can mis-score those mechanics; the oracle is the referee and the three are in `docs/ORACLE.md` with repros.
- Tasks are authored by us and checked only in Nucleation plus the oracle; they are easy relative to real contraptions. S50 and T3/T4 are what measure "any size".
- 263 of 1286 block ids cannot be loaded by the simulator (e.g. daylight detector, most buttons and plates).
- Entities and item flow: containers are unreadable from Nucleation's Python API; whole-farm throughput is out of scope for scoring.
